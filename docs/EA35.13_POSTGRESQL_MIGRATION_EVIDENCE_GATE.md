The ordinary CI workflow `.github/workflows/ci.yml` runs a selected pytest set on pushes to `main`/`dev` and pull requests targeting them. It does not provision PostgreSQL and does not run the migration history/checksum/production-entrypoint gate.

The separate `.github/workflows/postgres-concurrency.yml` provisions PostgreSQL 16, but its push trigger is limited to `postgres-concurrency-hardening`; its pull-request trigger targets `main`. It runs only `postgres/tests/test_concurrency.py`. This is not evidence that all canonical production migrations and runtime lifecycle operations passed on the audited HEAD.

## 2. Migration source findings

Inspected:
- `postgres/schema/001_concurrency.sql`
- `postgres/schema/002_canonical_production.sql`
- `postgres/schema/003_ea22_canonical_escrow_lifecycle.sql`
- `postgres/schema/004_ea25_durable_idempotency.sql`
- `postgres/schema/005_ea26_value_flow_persistence.sql`

Findings:
1. Migrations `002` and `003` both add `refund_destination`, `currency`, and `version` to `escrows`; both also replace the `escrows_state_check` constraint. The statements are partly guarded with `IF NOT EXISTS`, but duplicate ownership/order remains a migration-history clarity risk.
2. Migration `002` alters `escrows` and expects the base table to exist. The migration chain must prove the base schema is installed first on a clean PostgreSQL database.
3. The ordinary CI workflow does not apply all numbered SQL migrations in order against a clean PostgreSQL instance.
4. No evidence was found in the inspected workflow that records, for each migration, a durable applied-history row and content checksum, then compares those checksums against the exact checked-out commit.
5. The concurrency workflow pins PostgreSQL major version 16, but it does not record the effective server version alongside a full migration manifest and boot/runtime evidence.
6. The production factory's metadata `create_all` operation is not a substitute for a versioned SQL migration runner. It must not be treated as proof that the numbered SQL migration chain is complete or checksum-verified.

These are evidence gaps and ordering/duplication risks; no destructive migration was run during this audit.

## 3. Required gate bundle

A migration gate can pass only when one immutable commit SHA is attached to all of the following:

| Evidence | Required proof | Current state |
|---|---|---|
| Exact source | commit SHA, tree SHA, migration file list | Repository HEAD identified; no complete bundle |
| PostgreSQL version | server version output from the test instance | Missing |

| Lifecycle proof | CREATE/FUND/LOCK/RELEASE/REFUND/CANCEL/SETTLEMENT/READ tested against PostgreSQL | Missing as one integrated evidence bundle |
| Reconciliation | deep value-truth report matched; no unexplained orphan/missing evidence | Missing |
| CI provenance | successful workflow run linked to the same SHA | UNVERIFIED |
| Independent re-performance | separate rerun and preserved output | Missing |

## 4. Required execution order

1. Resolve migration ownership/order for duplicate `002`/`003` DDL without changing the frozen canonical architecture.
2. Add or verify a versioned migration-history table and checksum validation. Never rewrite a migration already applied to a shared database without an explicit reconciliation plan.
3. Run the entire migration chain against a fresh PostgreSQL 16 database.
4. Record PostgreSQL `server_version`, commit SHA, tree SHA, ordered migration names, SHA-256 checksums, history rows, and schema assertions as one artifact.
5. Run migrations a second time and verify the documented repeat-run behavior.
6. Boot the production entrypoint against that migrated database; assert that canonical Ledger authority is established and that no legacy authority is silently selected.
7. Run the canonical lifecycle and deep value-truth reconciliation on PostgreSQL.
8. Re-run CI at the same immutable SHA and preserve the workflow URL, run ID, job result, and artifact digest.
9. Have an independent rerun reproduce the results before closing the gate.

## 5. Decision

**Do not lock production readiness.**

Current evidence supports only that migration source files and workflow configuration were inspected. It does not establish successful clean PostgreSQL migration, checksum integrity, production boot, or lifecycle correctness. Keep the master production gate **IN PROGRESS / NOT LOCKED** until every required evidence item is attached to the same commit SHA.
